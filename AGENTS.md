# RIGS OS — notes for coding agents working on this repo

This repo is checked out on **every machine in the mesh** (`~/.rigs/app` by default) and runs there
as the RIGS daemon. A commit pushed to `main` reaches every machine through the self-updater, so
treat `main` as production.

## Layout

| Path | What |
| --- | --- |
| `bin/rigs.js` | CLI + supervisor (`rigs start` restarts the server on exit code 75 and rolls back a crash-looping update) |
| `src/server.js` | HTTP/WebSocket API. `/api/local/*` acts on this machine; `/api/nodes/<id>/*` proxies to any peer |
| `src/proxy.js` | Peer forwarding (`/api/nodes/<id>/*` → peer `/api/local/*`) and the App Cloud proxy `/api/nodes/<node>/apps/<id>/*`: local forward with Location/cookie/HTML/CSS rewriting + runtime shim, peer relay, raw WebSocket piping |
| `src/discovery.js` | Finds peers: online Tailscale devices probed on port 4719, plus static `peers` from config |
| `src/auth.js` | Who may call: loopback, same-owner tailnet devices (`tailscale whois`), or the mesh token |
| `src/sessions.js` | Claude Code / Codex / tmux / OpenRig / terminal session discovery, transcripts, attach, send |
| `src/chat.js` | JARVIS brains: Claude Code (`claude -p`), Codex (`codex exec --json`), Ollama (HTTP), and **Claude via Ollama** (`claude-ollama`: the same `claude -p` run, stream parsing, tool/trace spans and usage as the Claude brain, started with `ANTHROPIC_BASE_URL` = Ollama, a dummy `ANTHROPIC_AUTH_TOKEN`, blanked real credentials and `--model <Ollama model>` — env on that child only, never Claude's settings; own `claudeOllamaSessionId`/`claudeOllamaUsage` on the chat, cost recorded as 0; listed whenever the claude CLI is installed with `available`/`reason`, refused with a clear error when Ollama is down, empty or lacks the model). Hot-swappable mid-conversation |
| `src/router.js` | **Pre-routing** (`config.router`): before any brain sees a JARVIS request it is classified answer · implement · plan · continue and bound work is filed by RIGS itself (`opts.onWork`). Opening / showing / browsing a folder or file ("open my Downloads folder", "open ~/rigs-dev on magix-system", "show it in Files") is always answer: pure `isBrowseRequest` (short, a browse verb + a folder/file target, no work verb or fix/should/make-sure wording) answers it in `heuristicRoute` and overrides a model's implement/plan in `withWork`; pinned in `test/ui-open.test.js`. `preroute: false` (or `preroute` per `jarvis/send` request) skips it: the request goes to the JARVIS thread without the `[routed]` hint, the brain files work itself, and the trace keeps a router span marked `skipped`. Engines: `jev` (default) = a Jev-compatible `/v1/systemone` API — LocalJev, the App Cloud app `localjev` or `router.jev.url` — asked with a predecided `route` choice (~0.5 s), accepted at `jev.minProb`; `claude` = Haiku via `claude -p`; then keyword rules (a plain question Jev answers unsure about goes straight to the rules; Jev unreachable → the fallback, as before). `GET/POST /api/local/router`, `rigs preroute on|off|engine …` |
| `src/quick.js` | **Quick-task fast path** (`config.quick` `{ enabled: true, simple: {claude, claude-haiku-5-5, low}, standard: {claude, claude-sonnet-5-5, medium}, maxTurns: 8, timeoutMs: 90000 }`): a request the router classified `answer` (a question, web search, quick tool use, summary, short report) runs as one bounded `claude -p` turn on a cheaper model instead of the full brain — `chat.quickTurn`: same persona, rigs MCP and WebSearch/WebFetch, a fresh session (`--max-turns`, never resumes or changes the JARVIS thread's brain/model/session) with the last few messages as context, no project/jarvis_task/seat unless it files work itself. Pure and tested (`test/quick.test.js`): `quickTier`/`quickTierWhy` (haiku for a short question, lookup, single tool call, summary < ~2k chars; sonnet for search, research, report, compare, several steps, long text; a `tier` hint wins), `quickSettings`, `applyQuickPatch`, `quickOverride`, `resolveQuick` (only `answer`; per-request `quick` on `jarvis/send` = true\|false\|'haiku'\|'sonnet' beats config; without one, a request — or, when it names none, a JARVIS thread — on a non-Claude brain is left alone), `quickBrain` (tier → the provider/model/effort catalog), `parseEscalation`/`escalationGate`. The fast brain may reply `[[ESCALATE]] <reason>` (held back from the screen); that, its turn limit, an error or the timeout re-runs the request on the normal JARVIS thread with a hint of what it already ran (sequential, never both at once; a turn that already filed work is not re-run; the handover `status` event carries `reset: true` so the screen drops what the fast turn streamed). A fast turn is listed in `activeTurns` (work dashboard) with `lane: 'quick'`. Brain-turn span `meta.lane='quick'` + tier/model/effort, an `event` span `escalate`; ledger chat-turn and request records get `lane: 'quick'` (request also `tier`, `escalated`, `timeToReplyMs`). `quick: false` / `enabled: false` = the previous path exactly. `GET/POST /api/local/quick`, `rigs quick on\|off\|status`. **Local responder** (`config.quick.local`, off by default; design `docs/local-responder.md`): `localSettings` (validated block: `enabled`, `node` ('' = this machine; switching it on at a machine without a host makes that machine the host), `model` qwen3:8b, `tiers` ['haiku'], `tools` ⊆ `READ_ONLY_TOOLS` (8 rigs MCP tools that change no data: 7 lookups plus `ui_open`, which only opens the file browser on screen; config can narrow, never widen), `think` false, `numCtx` 16384, `keepAlive`, `maxRounds`, `guard`, `firstTokenMs` 2500, `timeoutMs` 30000); `quickSettings` keeps it only when configured (a config without it reads as before); `applyQuickPatch` merges/validates `local`; per-request `quick: 'local'` (`resolveQuick` adds `local: true`; a tier name adds `forcedTier`); pure `localResponder(q, config.quick, { self, text })` decides — on for an answer-routed fast-path turn whose tier is listed (or `quick: 'local'`), never for a Claude tier named on the request, and not for an ask about live data (`liveInfo`: weather, prices, scores, exchange rates, traffic, flights… — the local model has no web tools, so these stay on the Haiku turn, which searches). `chat.quickTurn` has the one branch: on → `runResponder` (src/responder.js) under `quick.local.timeoutMs`; its `unavailable` (nothing shown) → a `responder-fallback` event span and today's Claude turn, one after the other; `[[ESCALATE]]`, a tool outside the set, used-up rounds, an error after text or the timeout → `{ escalate }` → the full brain as today. Result/ledger/span: tier `'local'`, provider `ollama`, the model, cost 0 (chat-turn `tier`, request `tier` + `fallback`). `POST /api/local/quick {local:{…}}` also stamps the mesh-global settings. `rigs quick local on\|off\|status\|warm\|model <m>\|node <machine>` |
| `src/responder.js` | **Local live responder** (fast-path brain on a machine's own Ollama, `config.quick.local`): direct `/api/chat` tool loop (`localTurn`: `/api/ps` preflight — not loaded → warm in the background and report `unavailable` —, `think: false`, `num_ctx`, `keep_alive`, first-token timer → `unavailable`, HTTP error before output → `unavailable`, after output → `error`; tool calls only from `READ_ONLY_TOOLS` ∩ `tools`, run through `src/mcp.js` `TOOLS`, results cut to 6 kB; a name outside the set or `maxRounds` used up → `escalate`; **narration guard**: a reply that only announces a lookup (`narratedToolCall`) is kept as the spoken opener and `NUDGE`d once). ## Rules

- Node 22+, plain ESM JavaScript, no build step for the server. Keep dependencies minimal.
- Everything must work on macOS, Ubuntu (Wayland) and Windows. Use `src/util.js` helpers (`run`,
  `spawnCmd`, `which`) — they handle Windows `.cmd` shims and PATH for services.
- Never write to a user's real `~/.ssh`, `~/.claude*`, or `~/.codex` from tests; use `RIGS_HOME`,
  `RIGS_SSH_DIR`, `RIGS_NO_MIGRATIONS=1` and `RIGS_NO_AUTOUPDATE=1`, plus `RIGS_NO_OPENRIG=1` for any test or scratch server (otherwise it talks to the real OpenRig and queues fake "Sir: Dark mode" items into the live JARVIS overseer) (see `test/smoke.test.js`).
- New one-time steps for existing machines go in `src/migrations.js` (append-only); anything needing
  root goes through `src/rootsteps.js` so the user types one password in JARVIS.
- **Change policy — never commit to `main`.** `rigs dev <topic>` (MCP `rigs_dev_start`) gives you a
  worktree on `work/<machine>/<topic>` off the latest main; commit there, run `npm test` (and
  `npm run build` if you touched `ui/`), then `rigs propose` (MCP `rigs_propose`). The merge steward
  (`src/merge.js`) merges one branch at a time onto the latest main, re-runs build + tests on the
  merged tree, pushes and rolls out to every machine. Only a real conflict brings in a resolver agent
  (routing kind `merge`); failing checks come back to you. CI also runs on all three OSes after push.
- **Playbooks** (`docs/playbooks/*.md`): proven methods for recurring RIGS changes. A JARVIS request whose goal matches a
  playbook's `match` regex skips LLM planning: one agent follows it, then the final review. When a kind of request
  repeats, write one (front matter `title`, `match`, `size`; then the files, steps and checks). Examples: `ui-theme.md`,
  `p5-sketch.md`. Keep `match` narrow: a goal that only mentions "our theme" must not select the add-a-theme playbook.
- **Screen control is gated (`src/control.js`, design in `docs/full-access.md` §7).** Control is on by default, and
  a person or the kill switch switches it off per machine. `config.control` is in `patchConfig`'s blocked set, so no
  generic settings save or agent `POST config` can switch it back on. Only a confirmed human surface may do that. Do
  not add a route or MCP tool that bypasses the gate, the lease, the audit log or the kill switch. Every refusal is
  audited too, and a kill persists across restarts. Never migrate a machine back on after a person switched it off
  or the kill switch fired (`2026-10-17-control-default-on` leaves those as they are).
- Control safety rules (all of them, in every control change): every call goes through the gate, which checks
  enabled → allowFrom → lease → lock → backend + OS permission → rate limit, and only then takes the lease. Every action, refusal and switch is written to
  `logs/control.jsonl` (the audit log); the audit must be writable before a call touches the desktop. The kill
  switch (`rigs control off`, `POST /api/local/control/kill`, the ⌃⌥⌘⎋ hotkey on macOS) stops the backends at
  once and persists across restarts. Typing never uses Unicode `SetKeymap`: Wayland types keysyms and answers
  `unsupported` (501) for characters it cannot type.
- Agent-facing control tools (`mesh_screen`, `mesh_windows`, `mesh_control`, `mesh_access`) must ask Sir before
  use unless the task brief allows it for that machine. Nothing a tool or agent does may turn control back on.
- Changing default routing rules? Bump `RULES_VERSION` in `src/config.js` so non-customized machines pick them up.

## Ground rule: apps and applets go into the App Cloud

Every web app or applet built on the mesh is published so it opens inside JARVIS on any machine:

1. Serve it with **relative URLs** (it is reached under `/api/nodes/<node>/apps/<id>/`) and a cheap
   health endpoint (`/healthz`).
2. Give it a **launch recipe** for every OS it can run on. JARVIS uses it to spin the app up when someone
   opens it while it is down. `launch` takes, side by side:
   - `systemd`: a `systemctl --user` unit (enabled, so it survives reboots), used on **Linux only**;
   - `command` (+ optional `cwd`, default `~`, and `env`): a command line, used on any OS (on Linux only
     when there is no `systemd`);
   - `linux` / `darwin` / `windows`: `{ command, cwd, env }` for that OS, replacing the top-level recipe
     there (`linux` may give `{ systemd }`).

   ```json
   "launch": { "systemd": "szuf.service", "command": "~/szuf/run.sh",
               "windows": { "command": "python server.py --port 8787", "cwd": "~\\szuf" } }
   ```
   On Windows a command runs **without a POSIX shell**: its program is found on PATH (`.exe`, `.cmd`, `.bat`,
   `.ps1` through `util.spawnCmd`); only a line with cmd.exe syntax (`&&`, `|`, `%VAR%`) goes through cmd.exe.
   `launchFor(launch, platform)` in `src/apps.js` picks the recipe; each app's `launchHere` is the one its host runs.
   Old `{ systemd }` / `{ command }` recipes keep working unchanged.
3. **Register** it on its host: MCP `mesh_app_register` (or `POST /api/local/apps`, or `apps` in
   `~/.rigs/config.json` — picked up live). It appears in the galaxy (Apps), the left-panel Apps list
   and the ▦ launcher on every JARVIS; "open <name>" works by voice.

Code: `src/apps.js` (registry, health, `startApp`), `src/proxy.js` (proxy), `ui/src/apps.js` (windows).
